# MYR 운영 콘솔(`apps/myr-admin`) 화면 구성

2026-11-05 정리 · **2026-11-09 갱신**(교환·환불 7번 · 주문 6번 · 정산 정책 §9-6 반영) · **2026-11-12 갱신**(지급 — 0101 지급 건 · 0102 지급 상태 · 보류 이유 · 0103 지급 완료 기록 · §8-3 · §8-4). 크리에이터 콘솔 4번(상품 등록 · 판매 중 수정 심사 · 섹션별 반려)까지 끝난 뒤, 운영 쪽에 필요한 화면을 모았다.
처음 계획은 [docs/myr.md §4.3](myr.md). 이 문서는 **지금 DB 에 있는 것(0056~0081)과 터미널 스크립트로 대신하고 있는 것**을 기준으로 다시 짰다.
**만드는 시점: 인플루언서 콘솔을 마친 뒤**(2026-11-09 대표 결정) — 그 전까지는 아래 "지금 대신하는 것" 의 스크립트로 운영한다.

- 앱: `apps/myr-admin`(아직 없음 · M6) · 게이트 `profiles.role='admin'`(셀러리 `requireAdmin()` 복사) · noindex
- 권한: 운영자 id 는 서버 세션에서만 정한다(백엔드 원칙 6). RPC 는 service role 만 쓰고, 처리한 사람은 `reviewed_by` 처럼 운영자 user id 로 남긴다.
- 디자인 시안: **없음**. 크리에이터 콘솔(Claude Design "MYR Influencer Admin") 톤을 따르되 PC 우선(표 · 2열 비교)으로 만든다. 시안이 필요하면 아래 화면 목록이 그 요청서다.

## 1. 로그인 · 홈 (우선 1)

- **`/login`** — 이메일 · 비밀번호 · 관리자가 아니면 거부(안내만, 계정 존재 여부는 말하지 않음).
- **`/` 홈** — 숫자 카드. 누르면 해당 목록으로 간다.
    - 신규 심사 대기 N(가장 오래 기다린 것 "3일째")
    - 수정 심사 대기 N
    - 재고 0 인 판매 중 상품 N(승인 때 재고를 빠뜨린 것 — 샵에서 품절로 보인다)
    - 발송 대기 주문 N(0069 `myr_app_admin_ship_pending`)
    - 답변 없는 문의 N(24시간 넘은 것)
    - 새 초대 요청 N(만료 화면에서 "새 초대 요청하기" 누른 사람)
    - **교환 · 환불**: 회수 대기 N · 재발송 대기 N · 환불 재시도 필요 N(크론이 실패한 것) · 크리에이터 답변 기한(2일) 넘은 처리 대기 N
    - **정산**: 이번 정산일(매월 1일) 확정 대기 · 배송 완료 기록이 없는 출고 줄 N(정산에 못 들어간다) · 제조금액 미입력 판매 중 상품 N
    - **지급**(0102 · 0103): 지급 가능 N건 · 금액 합(`myr_payout_to_pay`) · 지급 보류 N건(이유별 — 사업자 정보 확인 전 · 운영 보류 · 세금계산서 미수취) · **지급일(매월 1일 13:00)이 지났는데 지급 완료 기록이 없는 지급 건 N** · 세금계산서 확인 대기 N(7-4 뒤)
    - 품절(판매 중 · 재고 0) 상품 N — 재고를 넣거나 판매 종료를 정한다

## 2. 상품 검수 (우선 1 · 크리에이터 4번과 짝)

### 2-1. 목록 `/products`

- **탭**: 신규 심사 · 수정 심사 · 판매 중 · 일시중지 · 반려 · 종료.
    - 임시저장(draft)은 크리에이터 작업 중이라 기본 탭에서 뺀다(필터로만).
    - 신규 심사 · 수정 심사 탭은 **오래 기다린 순**(제출 시각 오름차순), 나머지는 최근 수정순.
- **줄**:
    - 타일/사진 · 상품명 · 크리에이터(@핸들) · 카테고리 · 가격
    - 상태 칩 · "심사 N일째" 또는 "N일 전 승인"
    - 재고(남은 수량)
    - 수정 심사 중이면 "수정 심사 중" 칩을 같이 단다(판매 중 탭에서도 보이게).
- **필터**: 크리에이터 · 카테고리 · 검색(상품명 · 코드).
- **필요한 RPC(새로)**: `myr_app_admin_products(status, seller, q, limit)`.
    - 크리에이터 콘솔의 `myr_app_seller_products`(0071) 행 모양에 `seller` · `revision`(0074 `myr_product_open_revision`)을 더한 것.
    - 열린 수정본 기준은 이미 있는 `myr_product_open_revision` 하나를 쓴다.

### 2-2. 신규 심사 상세 `/products/[code]` (status = pending)

- **왼쪽: 샵 상세 미리보기**
    - 샵 `/p/[code]` 와 같은 순서로 그린다: 구매 패널 → 레시피 노트 → 01 왜 만들었나요 → 02 성분 → 03 섭취법 → 04 제품 정보 → 05 FAQ.
    - 비어 있는 선택 섹션은 "비어 있음(샵에서 숨김)"으로 보여 준다.
    - 섹션 블록마다 **[의견 달기]** 버튼을 둔다. 섹션 = 크리에이터 에디터 단계 1~7과 같은 번호(`lib/product-review.ts` `STEP_SECTION`).
- **오른쪽: 검수 패널**(sticky)
    - 크리에이터(이름 · 핸들 · 연락처) · 제출 시각 · 이전 반려 이력(있으면 그때 의견).
    - **의견 목록**: 섹션 선택(1 기본 정보 ~ 7 FAQ · 전체) + 문장. 여러 개 가능, 최대 10개 · 300자(`myr_reject_items` 와 같은 상한).
    - **자주 쓰는 의견** 칩(선택): "효능 · 최상급 표현", "의약품 오인 표현", "함량 근거 필요", "사진 해상도" 등. 문구는 운영팀이 정한다(§6 열린 결정).
    - **[반려]** — 의견 1개 이상 또는 사유 필수 → `myr_app_admin_review_product(id, 'reject', reason, admin, items)`.
        - 크리에이터 화면: "심사 결과" → "반려 내용 고치기"(의견 달린 섹션에 "수정 필요" 칩).
    - **[승인]** — **재고 입력을 같이 받는다**(필수 · 0 이면 경고).
        - 이벗 상품코드는 이벗 확정(E1-a) 뒤 필수.
        - → `approve` + 재고 저장. 지금 approve RPC 는 재고를 받지 않으므로 아래 "새로 만들 것" 참고.

### 2-3. 수정 심사 상세 `/products/[code]/revision` (판매 중 · 일시중지 + 대기 수정본)

- **머리**: "수정 심사" 칩 · 요청 시각 · "승인 전까지 샵은 지금 내용으로 판매 중".
- **본문: 2열 비교** — 왼쪽 "지금 샵", 오른쪽 "수정본".
    - **바뀐 섹션만 펼쳐서** 강조하고, 안 바뀐 섹션은 접어 둔다.
    - 섹션 묶음은 크리에이터 콘솔의 `changedSections`(`lib/product-edit.ts` `SECTION_KEYS`)와 **같은 함수**를 써야 한다(백엔드 원칙 1).
        - 이 함수를 `@sellery/myr-core` 로 옮겨 두 콘솔이 같이 쓴다.
        - 운영 스크립트 `revisions` 의 "바뀐 항목"도 지금은 키 단위 비교라, 옮길 때 섹션 단위로 맞춘다.
- **오른쪽 패널**: 2-2 와 같은 의견 목록(기본 대상 = 바뀐 섹션) · 이 상품의 지난 수정 이력(반려 · 반영 · 취소).
- **[반영 승인]** → `myr_app_admin_review_revision(id, 'approve', null, admin)`.
    - 상세 컬럼만 바뀌고 판매 상태 · 재고 · 마진 · 옵션 · 태그는 그대로다.
- **[반려]** → `myr_app_admin_review_revision(id, 'reject', reason, admin, items)`.
    - 크리에이터 화면: "수정 반려" → 심사 결과 → 반려 고치기. 샵은 그대로다.
- 상품이 그사이 판매 종료됐으면 수정본은 canceled(0074)라 이 화면에 안 들어온다. 운영팀이 상품을 반려 · 삭제했으면 승인은 `WRONG_STATUS` · `NOT_FOUND`.

### 2-4. 판매 중 상품 관리 (같은 상세 화면의 다른 상태)

- **판매 중 · 일시중지**:
    - [일시중지](`review_product` pause) · [재개](approve) — **운영만**(0083 · 크리에이터 콘솔에서 뺐다)
    - **[재고 수정]** — 재고 0 이면 샵은 품절(판매 상태는 그대로 · §9-6)
    - **[판매 종료]** — **운영만**(2026-11-09 결정 · 0082 `myr_app_admin_review_product(…, 'end')` · 크리에이터 [판매 종료]는 뺐다) · 열린 수정본은 취소
    - **제조 원장** 칸(→ 8-1): 제조금액 · 보증금 · 남은 제조금액
- **반려**: 보낸 의견 · 크리에이터가 다시 요청하면 신규 심사로 돌아온다.
- **종료**: 읽기 전용(주문 · 환불 이력 링크).

### 2-5. 새로 만들 것(상품)

| 무엇 | 이유 |
|---|---|
| `myr_app_admin_products(...)` 목록 RPC | 운영 목록 · 탭 카운트 · 크리에이터 필터 |
| `myr_app_admin_product(code)` 상세 RPC — 상품 + 열린 수정본 + 수정 · 반려 이력 | 2-2 · 2-3 화면 한 번에 |
| 재고 저장 — `myr_app_admin_review_product` 에 `p_stock` 을 더하거나 `myr_app_admin_set_stock(id, stock)` | 승인 때 재고 필수(결정 13 · 지금은 SQL) |
| `changedSections`(섹션 묶음)를 `@sellery/myr-core` 로 이동 | 크리에이터 "변경됨" 과 운영 "바뀐 섹션" 이 같은 판정 |
| 샵 상세 섹션 컴포넌트 복사(myr-shop `/p/[code]`) | 미리보기를 샵과 같은 모양으로(셀러리 코드 import 금지 · MYR 앱끼리는 복사) |
| (선택) 반려 · 승인 알림 메일 — 크리에이터에게 | 지금은 크리에이터가 콘솔을 열어야 안다 |
| ~~운영 판매 종료 RPC~~ — 0082 에서 `myr_app_admin_review_product` 에 `end` 를 더했다(사유 칸이 필요하면 그때 추가) | 판매 종료는 운영만(§9-6) |

### 2-6. 없어지는 것

`myr-products.mjs` 의 `review` · `revisions` · `review-revision` · `list`. `import` 와 `creators` 는 시드 · 대량 투입용으로 남길지 그때 정한다.

## 3. 크리에이터 (우선 1 초대 · 우선 2 관리)

### 3-1. 초대 `/sellers/invite`

- **[초대 보내기]**: 이메일 · 보낸 사람 이름 → 링크 발급 + 초대 메일(0070 `myr_app_admin_invite_create` · 메일은 크리에이터 콘솔 `/api/ops/invites` 와 같은 템플릿) · 링크 복사 버튼.
- **목록**: 대기 · 가입 완료 · 만료 · 취소 · **요청됨**(만료 화면에서 다시 요청) — `myr_app_admin_invite_list(state, limit)`.
    - 줄 동작: 재발송(이전 링크 무효) · 취소(`myr_app_admin_invite_revoke`).
- 없어지는 것: `myr-invites.mjs` · 크리에이터 콘솔의 `/api/ops/invites`(콘솔 간 `CRON_SECRET` 호출이 필요 없어진다).

### 3-2. 목록 · 상세 `/sellers` · `/sellers/[handle]`

- **목록**: 이름 · 핸들 · 계정 연결 여부 · 상품 수(판매 중/전체) · 상태(활성 · 정지) · 가입일.
- **상세**:
    - 연락처(`sellers.contact_phone` · 열람 기록)
    - 상품 목록(→ 2-1 필터)
    - 문의 응답률 · 최근 주문
    - **[정지 · 복구]**(`sellers.active` — 정지하면 콘솔 `/suspended` · 새 상품 저장 불가)
    - **[계정 연결]**(이미 있는 시드 크리에이터에 로그인 계정 — `myr-creators.mjs account` 대체)
    - **사업자 · 정산 정보**(0085 · 크리에이터가 가입 폼(선택 칸) · 내 정보에서 입력): 상호 · 사업자등록번호 · 대표자 · 세금계산서 이메일(초대 이메일) · 정산 계좌 — 원문 열람(열람 기록) · **[확인 완료]** / **[다시 입력 요청](사유)** — 화면에 띄운 값의 제출 시각을 같이 보낸다(그사이 바뀌면 STALE → 새 값으로 다시 그림) — `myr_app_admin_settle_infos` · `myr_app_admin_settle_info_check`(지금은 `myr-creators.mjs settle-info · settle-verify · settle-reject`). 홈 카드 "정산 정보 확인 대기 N"
    - **정산 요약**(→ 8): 상품별 남은 제조금액 · 보증금 상태 · 최근 정산 회차
    - **지급 이력**(→ 8-3): 회차별 지급 건 상태(지급 대기 · 지급 보류 + 이유 · 지급 완료 · 지급 없음) · 금액 · 이체한 날 · 가린 계좌 · 운영 메모 · 기록/취소 이력(`myr_payout_logs`)
    - 사업자 정보를 [확인 완료] / [다시 입력 요청] 하면 그 크리에이터의 지급 건이 트리거로 다시 정해진다(0102 `sellers_myr_payout_refresh` — 확인 완료면 지급 대기 · 아니면 지급 보류). 화면은 버튼 뒤 지급 건 상태를 다시 읽어 보여 준다(운영 보류 · 지급 완료는 바뀌지 않는다)
- 새로 만들 것: 크리에이터 목록 · 상세 · 정지 RPC(셀러리 0022~ 파트너 관리 패턴).

## 8. 정산 (우선 3 · §9-6 결정)

정책 요약: 판매가(공구가로 팔렸으면 공구가) × **60%** · **매월 1일 13:00(KST) 크론이 계산하고 바로 확정** · **배송 완료일이 지난달 이하이고 아직 정산 안 된** 줄 · 정산 뒤 환불은 **다음 회차 차감**(마이너스면 이월) · 제조금액은 **상품별**로 먼저 상계 · 다 갚은 회차에 **입금 확인된 보증금(제조금액 25%) 환급** · 원 미만 버림 · **제조 원장이 없는 상품만 보류**(운영이 원장을 넣고 확정) · 셀러는 사업자만(미확인이면 지급만 보류) · 세금계산서는 셀러 → MYR.
**지급(0101~0103)**: 회차마다 크리에이터 1명당 **지급 건** 1건(`myr_payouts`) — 금액 = 담긴 정산 줄 지급액 합(`myr_payout_amount` · 표에 숫자를 따로 두지 않는다). 상태는 지급 대기 · **지급 보류(+ 이유)** · 지급 완료 · 지급 없음(0원)이고 서버 한 곳(`myr_payout_auto_state`)이 정한다. 운영 보류 · 지급 완료는 사람이 바꾼다.

DB · 함수는 0087 이 다 있다(`myr_settlement_run` · `myr_settlement_confirm_held` · `myr_settlement_report` · `myr_mfg_*`) · 지급은 0101~0103(`myr_payout_*` · `myr_settlement_run_of`). 어드민은 이 함수를 부르는 화면만 만든다 — 계산을 화면에서 다시 하지 않는다(백엔드 원칙 1). 어드민 actor 는 `admin:<user id>` 로 넘긴다.

### 8-1. 제조 원장 `/manufacturing` · 상품 상세의 "제조 원장" 칸

- **원장 입력 대기**(맨 위 · `myr_mfg_pending`): ① **보류된 정산** — 상품 · 크리에이터 · 보류된 달 · 정산금 합계 · [제조금액 입력] → [보류 확정](`myr_settlement_confirm_held`) ② **판매 중인데 원장이 없는 상품** — 다음 회차에 보류될 후보(매월 1일 전에 채운다).
    - [보류 확정]을 눌러도 **돈은 다음 회차 지급 건에서 나간다**(2026-11-12 결정 · 0101). 버튼 옆에 "다음 정산(○월 1일)에서 지급돼요"를 보여 준다 — 크리에이터 정산 탭에도 "다음 정산에서 지급" 칩이 뜬다. 안 눌러도 다음 회차 크론이 같은 일을 한다.
- 상품별(`myr_mfg_ledger`): 차수 표(차수 · 제조금액 · 보증금 = 25% 버림 · **보증금 입금 확인일** · 환급 여부 · 메모 · 입력자 · 무효 표시) · 합계 · 상계 합계 · **남은 제조금액** · 보증금 입금 · 환급 합계.
- [제조 차수 추가](`myr_mfg_add`) — 재생산도 같은 버튼(2026-11-09 결정: 그 차수 제조금액을 남은 제조금액에 · 그 25% 를 보증금에). **0원 = "제조금액 없음" 명시**(보류를 풀 때).
- [보증금 입금 확인](`myr_mfg_deposit` · 날짜) — 환급은 입금 확인된 보증금만.
- **[금액 정정]**(`myr_mfg_fix` · 올바른 금액 · 사유 필수) — 올바른 금액으로 새 차수 + 잘못된 차수 무효를 한 번에(보증금 입금 확인일 옮김). 남은 제조금액 = 유효 차수 합 − 확정된 상계 합이라 **이미 상계한 금액은 빼고 남은 만큼만** 이후 회차에서 상계된다. 확정된 회차 금액은 그대로.
    - 올바른 금액이 이미 상계한 금액보다 작으면 거절(USED) + **덜 지급한 차액**(shortfall)을 보여 준다 — 시스템이 돌려주지 않는다(운영이 따로 지급).
    - 입금 확인된 보증금이 정정으로 달라지면 **보증금 차액**(deposit_diff)을 보여 준다 — 더 받았으면 따로 돌려주고, 모자라면 추가로 받는다.
- [차수 무효](`myr_mfg_void` · 사유 필수) — 차수를 통째로 없던 걸로(중복 입력 등). 지우지 않고 무효로 남긴다. 상계에 쓰였거나(USED · 차액 안내) 보증금을 환급한(REFUNDED) 차수는 무효 불가.
- 목록 필터: 남은 제조금액 있음 · 다 갚음 · 보증금 미입금 · 원장 없음.

### 8-2. 월 정산 `/settlements` · `/settlements/[YYYY-MM]`

- **회차 목록**: 정산월 · 계산 시각 · 실행(cron · script · admin) · 상품 수 · 확정 / **보류** 수 · 정산금 합계 · 상계 합계 · 보증금 환급 합계 · **지급 합계**(그 회차 지급 건 금액 합 — `myr_settlement_report.payout_total`) · 지급 진행(지급 완료 N / 지급 건 N · 보류 N).
- **회차 상세**(`myr_settlement_report`): 크리에이터 → 상품 단위 표.
    - 상태(확정 · **보류**) · 판매(그 회차에 처음 정산된 줄 — 줄 금액 − 계산 때 환불) · **정산 뒤 환불**(지난 회차 줄) · **이월**(지난 회차 마이너스) · **정산금(60% · 원 미만 버림)** · 남은 제조금액(이전) · **상계** · 남은 제조금액(이후) · **보증금 환급** · **지급액**(0원 가능 · 보류면 비어 있음).
    - 크리에이터 머리줄: **그 회차 지급 건** — 금액(`myr_payout_amount`) · 상태 문구(`myr_payout_status_label`) · 보류 이유(`myr_payout_hold_label`) · 지급 가능(`myr_payout_payable`) · 이체한 날(`myr_settlement_report.payouts[]` 그대로 · 화면이 사업자 정보 상태로 보류를 다시 판정하지 않는다).
    - 지급 건 금액 ≠ 그 회차 줄 지급액 합일 수 있다 — 지난 달 보류가 이 회차에 풀린 줄이 더해지고, 이 회차 보류 줄은 빠진다. 줄 표에서 "지급 건에 담김 · ○월분 · 다음 회차에서 지급"을 구분해 보여 준다(크리에이터 정산 탭과 같은 `myr_settlement_card_rows`).
    - 줄 단위로 펼쳐 보기(`myr_settlement_items` — 주문번호 · 배송 완료일 · 단가(공구 줄 표시) · 수량 · 그때 환불 · sale / 정산 뒤 환불 구분) — **읽기 RPC 추가 필요**(지금 보고는 줄 수만).
- **확정은 크론이 한다**(2026-11-10 결정) — 화면에 [확정] 버튼 없음. 보류 줄만 [보류 확정](8-1 과 같은 함수) — 안 눌러도 다음 회차 크론이 제조금액이 들어온 보류 줄을 먼저 해제해 그 회차 지급 건에 담는다. 손으로 먼저 확정해도 다음 회차 지급 건에 담긴다(0101). 회차 상세에 "보류 해제분" 줄을 원래 달과 함께 보여 준다.
- [회차 수동 실행] — 크론이 실패했을 때만(`myr_settlement_run` · 이미 있으면 already · 끝난 달만 · 순서 지킴).
- 경고: 배송 완료 기록이 없는 출고 줄(배송 중으로 오래 남은 줄 — 정산이 늦어진다) · 원장 없는 판매 상품 · 사업자 정보 미확인 크리에이터.

### 8-3. 지급 `/payouts` · `/settlements/[YYYY-MM]/payouts` (0101~0103)

지금은 `myr-settle.mjs to-pay` · `paid` · `unpaid` · `hold` · `release` · `report` 로 한다. 화면은 이 RPC 를 그대로 부른다 — 지급 가능 · 금액 · 상태 · 보류 이유를 화면에서 다시 계산하지 않는다(백엔드 원칙 1).

- **지급 목록**(그 달 · 기본은 "지급할 차례"):
    - 탭: **지급할 차례**(지급 가능 — `myr_payout_payable`) · 지급 보류(이유별) · 지급 완료 · 지급 없음(0원) · 전체.
    - 줄: 크리에이터 · 핸들 · 금액(`myr_payout_amount`) · 담긴 줄 수(지난 달 보류 해제분 표시) · 상태 문구 · 보류 이유 · 계좌(**가린 값** — `myr_mask_account`) · 이체한 날 · 메모.
    - 계좌 원문은 줄을 열고 **[계좌 보기]**로만(열람 기록 `sensitive_access_log` · 셀러리 0020 처럼 원문은 `sellers.bank_info` 에만) — 지금 `myr_payout_to_pay` 는 원문을 바로 돌려주니(스크립트용) 화면용 읽기 RPC 는 가린 값 + 따로 열람 RPC 로 나눈다.
    - **[이체용 내려받기]** — 지급할 차례 전체(크리에이터 · 은행 · 계좌 원문 · 예금주 · 금액). 은행 일괄 이체 양식은 지급 방식 결정(§9-9) 뒤. 내려받기도 열람 기록.
- **[지급 완료 기록]**(줄 · 여러 줄 선택) — `myr_payout_mark_paid`.
    - 입력: **이체한 날**(기본 오늘 · 한국 날짜) · 메모. 금액은 **화면이 다시 입력받아**(또는 이체 파일 금액) 서버 금액과 맞는지 서버가 확인한다(`AMOUNT_MISMATCH` 면 맞는 금액을 보여 줌).
    - 거절 코드를 그대로 안내: `NOT_PAYABLE`(보류 이유 표시) · `ALREADY_PAID`(이미 기록된 날) · `FUTURE_DATE` · `BEFORE_RUN`(회차 계산일 표시) · `BAD_DATE`.
    - 여러 줄을 한 번에 기록하려면 **일괄 RPC 추가 필요**(같은 이체일 · 줄마다 결과 — 일부 실패해도 나머지는 기록 · 지금은 한 건씩).
    - 기록하면 크리에이터 정산 탭 칩이 "지급 완료" · 지급일이 이체한 날로 바뀐다. **크리에이터 알림(메일)**은 없음 — §9 열린 결정.
- **[운영 보류]**(메모 필수) · **[보류 해제]** — `myr_payout_hold` · `myr_payout_release`. 지급 완료 · 0원은 보류 불가. 사람이 건 보류는 사업자 정보가 바뀌어도 풀리지 않는다. 크리에이터에게는 "운영팀 확인 중"만 보인다(메모는 운영만).
- **[지급 완료 취소]**(사유 필수) — `myr_payout_unmark_paid`. 잘못 기록했을 때만 — 실제로 보낸 돈을 되돌리는 기능이 아니다(송금 회수는 운영이 따로). 취소하면 자동 상태로 돌아가고 기록 · 취소 이력은 남는다.
- **지급 건 상세**(줄 열기): 담긴 정산 줄(상품 · 원래 달 · 지급액 — 회차 상세 8-2 와 같은 줄) · 상태 이력(`myr_payout_logs` + 보류/해제 시각 · 사람) · 지급 때 가린 계좌(`paid_bank`) · 그때 금액(`paid_amount`).
- 운영자 이름: RPC 의 `p_actor` 에 `admin:<user id>` 를 넘긴다(지금 스크립트는 `script`).
- 경고: 지급일이 지났는데 지급 대기로 남은 지급 건 · 사업자 정보 확인 대기 때문에 보류된 금액 합 · 세금계산서 확인 대기(7-4 뒤).
- 없어지는 것: `myr-settle.mjs` 의 `to-pay` · `paid` · `unpaid` · `hold` · `release`(`report` 의 지급 건 부분은 8-2 회차 상세로).

### 8-4. 세금계산서 수취 확인 `/tax-invoices` (작업 순서 7-4 · 세무 답변 대기)

크리에이터(사업자)가 MYR 에 세금계산서를 발행하고, 운영이 받았는지 확인해야 지급한다. **역발행 가능 여부 · 발행 금액(정산금 전체 vs 상계 뒤) · 작성일자**가 정해지면 만든다(§9-12).

- 크리에이터 콘솔: 달 상세 "지급 정보" 아래 "세금계산서" 칸 — 발행할 금액 · 작성일자 안내(서버 값) · 승인번호 입력 · 상태(제출 전 · 확인 대기 · 확인 완료 · 다시 제출 요청 + 사유).
- 운영 `/tax-invoices`: 확인 대기 목록(크리에이터 · 정산월 · 발행할 금액 · 승인번호 · 제출 시각) → 홈택스에서 대조 → **[수취 확인]** / **[다시 제출 요청](사유)**.
- 지급과 연결: 확인 전에는 지급 건이 **지급 보류 · 세금계산서 미수취**(`myr_seller_hold_reason` 에 이유 하나 더하기 · 표 제약에 `tax_invoice`) → 확인하면 트리거로 지급 대기(0102 와 같은 방식). 지급 완료 기록(`myr_payout_payable`)이 자동으로 막는다.
- 역발행이면 흐름이 바뀐다 — MYR 이 발행하고 크리에이터가 승인 · 승인번호 입력 칸 대신 "발행 요청 · 승인 대기" 상태.
- 그 전까지는 운영이 받았는지 직접 확인하고 `paid` 로 기록한다.
