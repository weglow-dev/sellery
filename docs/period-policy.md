# 셀러리 판매 기간·링크 보호 정책

> 최종 수정: 2026-09-15 · 근거: 코드 상수(js/00-core.js, js/02-state.js 등) + 브랜드/인플루언서 제안서(2026.09) · 상태: 프로토타입 기준(실서비스 전 확정 필요)

셀러리의 협업판매는 **기간 한정**으로 열렸다 닫힙니다. 이 문서는 (1) 판매 기간을 정하고 승인하는 흐름, (2) 같은 상품에 여러 인플루언서가 들어올 때의 우선순위·재고 배정, (3) 판매 중 브랜드가 바꿀 수 없는 것, (4) 판매 링크의 형식·활성화·만료, (5) 인플루언서 링크로 들어온 고객을 경쟁 판매로부터 보호하는 규칙을 다룹니다. 수수료·정산 금액 계산은 `settlement-policy.md`, 등급 산정은 `grade-policy.md`를 참고하세요.

문서 안의 **"미정(코드 미구현)"** 표시는 화면 문구나 입력 힌트로만 존재하고 코드가 강제하지 않는 항목입니다. 실서비스 전에 구현할지, 문구를 고칠지 결정이 필요합니다.

## 1. 기본 원칙

| 원칙 | 내용 | 코드 근거 |
|---|---|---|
| 기간 한정 | 판매는 확정된 시작일~종료일에만 열리고, 종료 다음 날 자동으로 교환·환불 기간(CLEARING)으로 넘어간다 | `autoTick` |

| 재고 배정 | 확정·진행 중 캠페인에 이미 배정된 수량을 뺀 잔여 재고 안에서만 배정한다 | `allocated`, `stockLeft` |
| 조건 잠금 | 확정·진행·환불기간 중인 판매가 하나라도 있으면 그 상품의 판매가·수수료율은 바꿀 수 없다 | `productModal`/`saveProduct`의 `locked` |
| 링크 보호 | 인플루언서 링크로 들어온 고객에게는 같은 상품·같은 카테고리의 다른 판매를 보여주지 않는다. 새로고침·홈 이동에도 유지 | `LINKCTX`, `custVisible` |

## 2. 일정 제안 → 승인 흐름

### 2.1 관련 상태

| 상태 | 화면 라벨 | 차례(turn) | 의미 |
|---|---|---|---|
| `TESTING` | 테스트 중 | 인플루언서 | 샘플 수령 후 "진행 → 일정 제안" 또는 "패스". 수령 확인 시 `testDue` = 수령일 + 14일이 기록·표시되지만 **표시 전용**(아래 미정 항목) |
| `SCHEDULE_PROPOSED` | 일정 승인 대기 | 브랜드 | 인플루언서가 기간·수량을 제안. `propStart / propEnd / propQty`에 임시 저장 |
| `SCHEDULE_CONFIRMED` | 일정 확정 | — | 브랜드 승인. `start / end / qty`로 확정, 캘린더에 표시, 재고 배정·기간 점유 시작 |
| `LIVE` | 판매 진행중 | — | 시작일 도래 → 판매 링크 활성화 |
| `CLEARING` | 교환·환불 기간 | — | 종료일 경과 → 링크 만료(구매 불가), 정산 기준일 = 종료 + 21일 |
| `SETTLED` | 정산 완료 | — | 관리자 정산 실행 후 |

전체 흐름(`FLOW`): 샘플요청 → 샘플승인 → 배송 → 테스트 → **일정제안 → 일정확정 → 판매 LIVE → 환불기간 → 정산**.

> **미정(코드 미구현) — 테스트 기한 14일:** `testDue`는 `receiveSample`(수령 확인)과 `regongu`(재판매)에서 오늘 + 14일로 기록되고, 인플루언서 홈 할 일 목록·브랜드 캠페인 행·스레드 카드("기한 M/D 까지")·캘린더 "테스트 마감" 이벤트에 **표시만** 된다. 기한이 지나도 자동 패스되지 않고, 일정 제안도 막히지 않는다(`TESTING` 카드의 "진행할게요 → 일정 제안"·"이번엔 패스" 버튼에 날짜 가드 없음). `autoTick`은 `SCHEDULE_CONFIRMED → LIVE`, `LIVE → CLEARING` 두 전이만 처리한다. **제안서 표기:** 브랜드 p.5 "03 인플루언서 테스트 — 직접 써보고 결정 · 14일", 인플루언서 p.5 "03 직접 써보기 — 기한 14일" · p.11 "테스트 기한(14일) 안에 진행 또는 패스를 고르시면 됩니다" — 양쪽 제안서 모두 규칙으로 제시하지만 코드는 표시만 한다. 실서비스 전에 기한 경과 시 자동 패스·일정 제안 차단을 구현할지, 제안서 문구를 권장 기한으로 완화할지 결정 필요.

> **패스(`passCamp`):** `PASSED`로 전이할 뿐 등급·노출·🥬에 페널티가 없다(인플루언서 p.11 "패스해도 괜찮아요 — 등급·노출·다음 제안에 아무 영향이 없어요"와 일치). 단 `hadFreeSample`은 `REJECTED`·`DECLINED`만 제외하므로 **패스한 캠페인도 그 상품의 무상 샘플 1회를 소진한 것으로 계산**되어, 같은 상품을 다시 요청하면 "샘플 구매"로만 진행된다 — "다음 제안에 아무 영향이 없어요"와 이 부분은 어긋난다(`sample-policy.md` §5·§10 참조).

### 2.2 인플루언서의 일정 제안 (`scheduleModal` → `proposeSchedule`)

| 입력 | 기본값 · 입력 힌트 | 실제 검증 |
|---|---|---|
| 시작일 | 기본값 D+7. 입력 필드에 `min` = 내일(D+1) | **미검증**(코드 미구현): 직접 입력한 과거 날짜도 그대로 접수된다. 승인되면 다음 렌더의 `autoTick`이 곧바로 `LIVE`로 바꾼다 |
| 기간 | **3일 / 5일 / 7일** 중 선택(기본 5일) | 선택 상자이므로 세 값만 가능. 종료일 = 시작일 + 기간 − 1 |
| 희망 배정 재고 | 기본값 = min(500, 잔여 재고). 입력 필드에 `min=50 step=50 max=잔여` | 50개 단위·최소 50은 **미검증**(코드 미구현): 1개·37개도 접수된다. 실제 검증은 아래 3·4(수량 ≤ 0 · 잔여 초과)뿐 |
| 참고 표시 | "이 상품의 확정 기간" — 같은 상품의 `SCHEDULE_CONFIRMED`/`LIVE` 캠페인 기간과 보유 인플루언서 핸들 목록("M/D – M/D @핸들 확정") | 보유자 **등급은 표시하지 않는다**(9장) |

> **제안서 표기:** 인플루언서 p.5 "04 일정 제안 — 내가 날짜를 정해요", p.12 STEP 3 "원하는 판매 기간과 수량을 제안하면 브랜드가 승인해요" — 기간을 자유롭게 정하는 것처럼 읽히지만 코드는 **3·5·7일** 세 가지만 허용한다(`schLen` 선택 상자). 브랜드 p.8·인플루언서 p.9의 캘린더 예시에 그려진 기간(버닝온 8–11 = 4일, 치팅온 12–13 = 2일)은 코드로 제안할 수 없는 길이다. 실서비스 전에 선택지를 넓힐지(자유 입력 + 최소·최대 일수), 제안서에 "3·5·7일 중 선택"을 명시할지 결정 필요.

모달에는 `<form>`이 없어 HTML `min`/`step`/`max`는 브라우저 입력 보조일 뿐 제출을 막지 않는다. **실제 규칙은 아래 검증 목록이 전부다.** 제안 버튼을 누르면 다음 순서로 검증하고, 하나라도 걸리면 토스트로 사유를 안내하며 제안은 저장되지 않는다.

1. 시작일 미선택 → "시작일을 선택하세요"
2. **등급 우선 기간 판정** `periodBlock(productId, start, end, 자기 캠페인 제외, sellerId)` → 차단 시 "이 기간은 ○○ 등급 인플루언서가 선점했습니다 — 플래티넘 이상만 함께 판매할 수 있어요"
3. 수량 ≤ 0 → "배정 재고를 입력하세요"
4. **재고 가드** 수량 > `stockLeft` → "배정 가능한 재고를 초과했어요 (잔여 n개)"

통과하면 `SCHEDULE_PROPOSED`로 전이하고 스레드에 "인플루언서가 판매 일정을 제안했습니다 · M/D – M/D · 재고 n"이 기록된다.

### 2.3 브랜드의 승인 / 반려 (`confirmSchedule` / `rejectSchedule`)

브랜드 홈 "승인·처리 대기" 목록과 DM "요청함" 목록은 **진입점**일 뿐이다 — 행 전체가 스레드 열기(`open`)이고 행 끝의 "승인" 버튼에는 별도 액션이 없어 누르면 스레드가 열린다. 실제 승인·반려는 캠페인 스레드의 "일정 승인" 카드에서만 처리한다. **승인 시점에 같은 검증을 다시 한다** — 제안 이후 상위 등급이 그 기간을 선점했거나 잔여 재고가 줄었을 수 있기 때문이다.

| 승인 시 검사 | 실패 시 안내 |
|---|---|
| `periodBlock` 재판정 | "제안 이후 ○○ 등급 인플루언서가 이 기간을 선점했어요 — 반려하고 재제안을 요청하세요" |
| `propQty ≤ stockLeft` | "잔여 재고(n개)보다 많은 수량입니다 — 재고를 늘리거나 반려하세요" |

- 승인 → `start/end/qty` 확정, `SCHEDULE_CONFIRMED`, 토스트 "일정 확정 — 캘린더 잠금".
- 반려 → `TESTING`으로 되돌아가 인플루언서가 다른 기간으로 재제안한다. `testDue`는 갱신되지 않지만 표시 전용이라(2.1) 기한이 지났어도 재제안은 막히지 않는다.

### 2.4 재판매 우선권 (제안서 상충 — 브랜드 승인 생략)

정산 완료(`SETTLED`)된 판매의 "🔁 재판매 제안" 버튼은 샘플 단계를 건너뛴 `TESTING` 캠페인(`regongu: true`)을 새로 만든다. 이때 인플루언서가 셀러리 샵의 **재판매 우선권(30일 · 2🥬)** 을 보유 중이면(`passActive(seller,'regongu',30)`), 일정 제안이 브랜드 승인 없이 **즉시 `SCHEDULE_CONFIRMED`** 된다. 2.2의 등급 우선·재고 검증은 그대로 적용된다.

> 샵 설명 문구 "겹치는 기간 제외"는 **구 정책(하드 독점) 문구**다. 실제 검증은 2.2와 같은 `periodBlock`(플래티넘 이상이 선점한 기간만 차단)·재고 가드이며, 골드 이하끼리 겹치는 기간은 제외되지 않고 그대로 즉시 확정된다. 실서비스 전 문구 수정 필요.

> **제안서 표기:** 브랜드 p.5 "04 일정 제안·승인 — 등급 우선 기간 + 재고 배정", 인플루언서 p.12 STEP 3 "원하는 판매 기간과 수량을 제안하면 브랜드가 승인해요" — 양쪽 제안서 모두 브랜드 승인 단계를 약속하지만, 재판매 우선권은 **브랜드에게 묻지 않고** 기간과 수량(잔여 재고 전량까지 — 상한은 `stockLeft`뿐)을 확정한다. 인플루언서가 2🥬로 산 아이템이 브랜드의 기간·재고 결정권을 대신하는 구조이므로 단순 미기재가 아니라 **상충**이다. 실서비스 전 결정 항목: 브랜드가 상품별로 우선권 적용을 켜는 옵트인, 아이템 폐지, 또는 샵 문구·제안서 문구 수정 중 택일.

> **미정(코드 버그) — 샵 카드 만료 표시:** `SHOP.seller.regongu`에 `days` 필드가 없어(브랜드 `datapass`만 `days:30`) 셀러리 샵 카드는 한 번 사면 `passActive(ent, id, undefined)`가 항상 참 → 30일이 지나도 "보유 중"으로 표시되고 재구매 버튼이 나오지 않는다. 효과 판정(`regongu`·`proposeSchedule`의 `passActive(…,'regongu',30)`)은 30일에 끝나므로 **계정당 사실상 1회용**이 된다. 코드 수정 과제: `regongu`에 `days:30` 추가(10장의 `homefeature`와 같은 원인).

## 3. 등급 우선 기간제

### 3.1 우선 등급 경계

`PRIORITY_TIER = '플래티넘'`. 인플루언서 등급은 최근 3개월 확정 매출(`m3Sales`)로 산정하며, `tierIdx(등급) ≤ tierIdx('플래티넘')`인 등급이 우선 등급이다.

| 등급 | 3개월 확정 매출 기준 | 기간 우선권 | 관련 혜택(코드 `perk` 발췌 · 원문 순서) |
|---|---|---|---|
| 블랙 | 1억 이상 | **있음** | 판매 기간 우선권 · 독점권 우선 협상 |
| 다이아 | 5,000만 이상 | **있음** | 독점권 신청 · 판매 기간 우선권 |
| 플래티넘 | 3,000만 이상 | **있음** | 신상품 우선 제안권 · 판매 기간 우선권 |
| 골드 | 1,500만 이상 | 없음 | — |
| 실버 | 800만 이상 | 없음 | — |
| 브론즈 | 300만 이상 | 없음 | — |
| 스타터 | 0 이상 | 없음 | — |

### 3.2 판정 로직 (`periodHolders` → `periodBlock`)

1. **기간 보유자** = 같은 상품의 `SCHEDULE_CONFIRMED` 또는 `LIVE` 캠페인 중(자기 캠페인 제외) 제안 기간과 겹치는 것. 겹침은 **양 끝 포함**: `!(제안종료 < 보유시작 || 제안시작 > 보유종료)` — 하루라도 닿으면 겹침.
2. 신청자가 우선 등급이면 → **항상 허용**(null 반환).
3. 신청자가 골드 이하이고, 보유자 중 우선 등급 인플루언서가 한 명이라도 있으면 → **차단**(그 인플루언서 객체 반환 → 토스트에 등급 표시).
4. 보유자가 전부 골드 이하이면 → 허용(기간 공유).

| 신청자 \ 겹치는 기간 보유자 | 없음 | 골드 이하만 | 플래티넘 이상 포함 |
|---|---|---|---|
| 플래티넘 · 다이아 · 블랙 | 허용 | 허용 | 허용 |
| 골드 · 실버 · 브론즈 · 스타터 | 허용 | 허용 | **차단** |

우선권은 **신규 진입 판정에만** 쓰인다 — 이미 확정된 골드 이하 캠페인은 밀려나지 않고, 플래티넘 이상이 골드 보유 기간에 들어오면 두 판매가 **함께 진행**된다. 확정·LIVE 캠페인을 재판정하거나 취소하는 코드는 없다(`autoTick`은 LIVE·CLEARING 전이만).

### 3.3 판정에 포함되지 않는 것

- `SCHEDULE_PROPOSED`(승인 대기)는 기간을 점유하지 않는다 → 같은 기간에 여러 제안이 동시에 들어올 수 있고, 먼저 승인된 쪽이 점유한다.
- `CLEARING`·`SETTLED`(종료된 판매)는 기간을 점유하지 않는다.
- 상품 독점권(`exclusiveSellerId`)은 별도 정책이다(→ `grade-policy.md`). 독점 인플루언서가 확정된 상품은 **샘플 요청·브랜드 제안·제안 수락 단계에서만** 다른 인플루언서를 막는다(`sampleBtnHtml` "독점 잠김" · `reqSample` · `confirmInvite` · `acceptInvite`). 그래서 보통은 기간 판정까지 오지 않지만, **독점 승인(`approveExcl`) 전에 이미 생성된 다른 인플루언서의 캠페인(샘플 요청 단계부터 어느 상태든) 및 재판매(`regongu`) 캠페인은 막히지 않는다** — `approveSample`·`shipSample`·`receiveSample`·`scheduleModal`·`proposeSchedule`·`confirmSchedule`·`periodBlock` 어디에도 `exclusiveSellerId` 검사가 없어 샘플 승인·발송·수령·일정 제안·승인이 그대로 진행된다(코드 미검사 · 미정). `approveExcl`은 `exclusiveSellerId`만 기록할 뿐 기존 캠페인을 건드리지 않는다. 시드가 그 예다: p1(버닝온)에 s4의 독점 신청 x1이 대기 중인 동안 c7(하늘 · p1)은 `SAMPLE_REQUESTED` — 브랜드가 x1을 승인해도 c7은 샘플 승인부터 일정 확정까지 그대로 간다.
- 판정은 **제안 시**와 **승인 시** 두 번만 실행되며, 캘린더에 "배정 불가" 셀을 미리 표시하지도, 제안 모달의 확정 기간 목록에 보유자 등급을 표시하지도 않는다(9장).

> **제안서 표기:** 브랜드 제안서 p.3의 문제 제기("03 판매가 서로 겹쳐요 — 같은 주에 여러 채널이 같은 상품을 풀면, 서로의 판매를 나눠 갖게 됩니다"), 브랜드 p.8과 인플루언서 제안서 p.9의 헤드라인 "판매 기간이 겹치지 않고", 인플루언서 제안서 p.13의 "기간 독점"은 모두 하드 독점을 암시하고, 캘린더 예시에는 "배정 불가"·"타 판매 확정" 셀이 그려져 있다. 코드는 **기간 공유 + 등급 우선**(2026-09-14 변경)이며 하드 독점이 아니다 — 보유자가 전부 골드 이하이거나 신청자가 플래티넘 이상이면 **같은 상품·같은 주의 겹치는 판매가 그대로 허용**된다(3.2 표). 같은 페이지 본문("기간은 열어두되, 플래티넘 이상이 확정한 기간에는 플래티넘 이상만")과 인플루언서 제안서 p.2는 코드와 일치한다. 인플루언서 제안서 p.6 "다이아 이상 상품 독점권 신청 가능"은 독점권 정책(`grade-policy.md`)이며, 위 항목대로 독점 승인 전에 이미 진행 중이던 캠페인까지 막지는 않는다. 다만 인플루언서 p.2 "플래티넘 이상이 잡은 기간에는 플래티넘 이상만 함께 판매합니다"와 p.4 "플래티넘 이상이 잡은 기간은 상위 등급만"은 3.2의 **진입 전용** 규칙보다 강하게 읽힌다 — 먼저 확정된 골드 이하 판매는 그 기간에 그대로 남아 함께 판매한다. 브랜드 p.8 "플래티넘 이상만 추가로 들어옵니다"가 정확한 표현이다. 이렇게 같은 주에 겹치도록 허용된 판매는 링크 컨텍스트 없는 판매센터 방문자에게 나란히 노출된다(8.2 첫 줄). 또한 **시드에는 플래티넘 이상 공개 인플루언서가 없어**(지유 `m3Sales` 1,560만 · 혜린 2,284만 → 둘 다 골드; 다이아인 s4·s5는 비공개이고 캠페인이 없다) 등급 우선 차단과 브랜드 p.6 "지유 플래티넘 · 혜린 다이아", p.8 "배정 불가" 예시는 시드 데이터로 재현되지 않는다 — 시드 등급 불일치 자체는 `grade-policy.md` 항목.

## 4. 재고 배정

| 항목 | 규칙 |
|---|---|
| 배정 합계 `allocated(pid)` | 같은 상품의 `SCHEDULE_CONFIRMED` + `LIVE` 캠페인 `qty` 합계(자기 캠페인 제외). **기간이 겹치는지와 무관하게** 전부 합산한다 |
| 잔여 재고 `stockLeft` | `max(0, 상품 재고 stock − allocated)` |
| 제안 시 | 희망 수량 ≤ 잔여 재고(모달 max 값 + `proposeSchedule` 가드) |
| 승인 시 | `propQty ≤ 잔여 재고` 재확인. 초과 시 브랜드가 재고를 늘리거나 반려 |
| 배정 해제 | 종료(`CLEARING`)·정산(`SETTLED`)되면 합산에서 빠진다 → 다음 판매에 재배정 가능 |
| 판매 중 잔여 | 구매 페이지 잔여 = `qty − 결제 완료 수량`. 0이 되면 구매 버튼 "품절" 비활성 |
| 브랜드 재고 수정 | 상품 수정 모달에서 언제든 가능(가격 잠금과 무관). `saveProduct`는 `stock`을 `allocated`와 비교하지 않는다 |
| 확정 후 재고 감소 | **미정(코드 미구현)** — 확정·LIVE 배정 합계보다 낮게 `stock`을 줄여도 저장이 막히지 않고 캠페인 `qty`도 줄지 않는다. 구매 페이지·`buyNow`는 캠페인 `qty − 결제 수량`으로 계속 판매하며, `stockLeft`는 0으로 클램프되어 초과 배정을 알리는 표시가 없다 |

시드 예시: 버닝온(p1) 재고 2,000 중 지유 LIVE 800 + 혜린 확정 1,000 = 1,800 배정 → 잔여 200.

> **제안서 표기:** "이미 배정된 수량을 빼고 남은 만큼만 배정됩니다. 품절 사고가 나지 않아요"(브랜드 p.8) — 가드는 **제안·승인 시점**(`proposeSchedule`/`confirmSchedule`)에만 실행된다. 확정 이후의 재고 수정은 검증되지 않으므로(위 "확정 후 재고 감소" 행) "품절 사고가 나지 않아요"는 코드가 끝까지 보장하는 약속이 아니다 — 미정(코드 미구현): 배정 합계 미만으로 줄이는 저장을 막을지, 경고만 할지 결정 필요. 또 코드는 겹치는 기간만이 아니라 확정·진행 중인 **모든** 배정을 뺀다.

## 5. 판매가·수수료율 잠금

`locked` = 해당 상품에 `SCHEDULE_CONFIRMED` / `LIVE` / `CLEARING` 상태의 캠페인이 하나라도 있음.

| 잠기는 항목(입력 비활성) | 잠기지 않는 항목 |
|---|---|
| 소비자가 `cp` · 판매가 `gp` · 총 수수료율 `rate` | 상품명 · 한 줄 설명 · 카테고리 · 썸네일/상세 이미지 · 재고 · 샘플 내용/샘플 정책 · 옵션 · 독점권 오퍼 |

- 잠금 안내: "진행 중·확정된 판매가 있어 **판매가·수수료율은 변경할 수 없습니다**(신뢰 보호). 재고·샘플 정책·옵션·이미지·독점권은 수정 가능합니다."
- 잠기지 않은 상태에서 노출 중(`listed`) 상품의 판매가·수수료율을 바꾸면 **검수 대기(`pending`)로 되돌아간다**("판매가·수수료율 변경 — 재검수 대기로 전환됩니다").
- 총 수수료율 입력 필드 힌트 11~50%(HTML `min`/`max`) — **저장 시 검증 없음**(코드 미구현). `saveProduct`는 입력값에서 플랫폼 10%p를 뺀 뒤 인플루언서 몫 **최소 5%** 만 보장한다(`Math.max(5, 입력 − 10)`). 상한이 없어 80을 입력하면 인플루언서 몫 70%로 그대로 저장된다.
- 노출 중단(`paused`)은 새 샘플 요청만 막고 진행 중 판매는 유지한다. 진행 이력이 있는 상품은 삭제할 수 없다.
- **브랜드 가격 약정(같은 기간 타 채널 최저가 금지) — 미정(코드 미구현).** 고객 화면은 브랜드를 대신해 이 약속을 하고 있다: FAQ "브랜드가 셀러리에 등록한 판매가로만 판매되고, 같은 기간 다른 채널에서 더 낮은 가격을 제시하지 않기로 약정합니다", 홈 "기간 한정 가격" 카드 "같은 기간, 다른 곳에서 더 낮은 가격은 없습니다", 홈 태그라인 "지금 진행 중인 최저가 상품". 그러나 브랜드가 이 약정에 동의하는 절차도, 타 채널 가격을 검증·기록하는 코드도 없다(등록 시 동의 체크·위반 시 처리 모두 미정). 브랜드는 상품을 등록하는 순간 고객에게 이 약속이 제시된다는 점을 알아야 한다.

> **제안서 표기:** "확정된 뒤에는 브랜드가 판매가·수수료율을 바꿀 수 없어요"(인플루언서 p.9) — 일치. "진행 중인 상품은 판매가·수수료율을 바꿀 수 없습니다"(브랜드 p.8)보다는 코드가 **넓다** — 잠금은 `SCHEDULE_CONFIRMED` 시점(판매 시작 전)부터 환불 기간(`CLEARING`)까지 이어지므로, 브랜드는 확정~시작일 사이에도 가격을 조정할 수 없다. 브랜드 제안서 문구를 "확정된 뒤에는"으로 맞추는 편이 정확하다. 브랜드 p.8 "가격 정책 보호 — 상시 최저가가 아니라 기간 한정 특가예요"는 고객 화면 문구로만 구현되어 있다(약정 동의·검증 미구현 · 위 항목).

## 6. 판매 링크

| 구분 | 형식 | 비고 |
|---|---|---|
| 화면 표시·복사 형식 | `sellery.co.kr/s/{핸들(@ 제외)}/{판매번호}` 예) `sellery.co.kr/s/jiyu_beauty/c1` | 캠페인 스레드 · 인플루언서 홈 카드 · 구매 페이지 상단 · 인증 모달. "링크 복사"는 `https://`를 붙여 클립보드에 복사 |
| 프로토타입 진입 주소 | `index.html#s/{판매번호}` 또는 `index.html#link/{판매번호}` (예 `#s/c1`) | 대소문자 무관. 판매번호가 존재하는 캠페인이면 상태와 무관하게 진입 가능. **핸들은 라우팅에 쓰이지 않음** |
| 상세페이지 미리보기 | `sellery.co.kr/p/{상품ID}` | 브랜드 상품 관리 → "상세페이지". 판매 링크 발급 전 레이아웃 확인용, 구매 불가 |

- **활성화:** `SCHEDULE_CONFIRMED` 캠페인은 시작일이 오늘 이하가 되는 순간 `autoTick`이 `LIVE`로 바꾸고 스레드에 "판매 시작 시각 도래 — 판매 링크 자동 활성화 (스케줄러)"를 남긴다. 확정 직후 카드 문구: "시작 M/D (D-n) — 시작 시각에 링크가 자동 활성화됩니다."
- **인증 확인:** 구매 페이지 상단 띠 "셀러리 인증 판매 · 결제 보관 · 21일 환불 보호 · 인플루언서 채널 인증 ✓"를 누르면 인증 링크(유효) · 판매 인플루언서와 등급 · 인증 채널 · 공급 브랜드(등급·사업자번호) · 판매 기간 · 결제·정산 방식이 표시된다. 미리보기(`p:` 링크)에서는 열리지 않는다.
- 링크로 들어온 방문자는 고객 화면에 고정되고 상단 역할 탭(인플루언서/브랜드/관리자)이 숨겨진다(`lockedRole`).
- 단, 셀러리 소개 하단의 "브랜드 센터"·"인플루언서 센터" 버튼(`goCenter`)은 `lockedRole`을 해제하고 해당 센터 홈으로 이동한다 — 고객 화면 안에서 고정을 벗어날 수 있는 **프로토타입 편의 경로**다. 이 경로로 나가도 `S.linkCtx`(링크 보호, 8장)는 지워지지 않는다.

> **제안서 표기:** "sellery.co.kr/s/내핸들/판매번호"(인플루언서 p.9) — 표시 형식은 일치. 실서비스 도메인 라우팅은 미정(코드 미구현: 프로토타입은 해시 `#s/cN`).

## 7. 판매 종료 · 링크 만료 후 흐름

| 시점 | 전이 | 근거 |
|---|---|---|
| 시작일 ≤ 오늘 | `SCHEDULE_CONFIRMED` → `LIVE` | `autoTick` (페이지 렌더 시마다 실행) |
| 종료일 < 오늘 (종료 다음 날) | `LIVE` → `CLEARING`. 스레드 "판매 기간 종료 (스케줄러) · 교환/환불 기간 시작 · 정산 예정 M/D" | `autoTick`. 종료일 당일까지 구매 가능 |
| 정산 기준일 = 종료일 + **21일** (`CLEAR_DAYS`) | 관리자 "정산 실행" 가능 → `SETTLED` | `settleDue`, `vAdminSettle`, `runSettle` |

구매 페이지의 상태별 표시:

| 캠페인 상태 | 히어로 배지 | 버튼·안내 |
|---|---|---|
| `LIVE` | "D-n 마감" / 종료일 당일 "오늘 마감" | **구매하기** (잔여 0 → "품절" 비활성) · "M/D–M/D 한정 · 잔여 n개 · n개 판매됨 · 결제 시 셀러리 안전결제로 이동" |
| `SCHEDULE_CONFIRMED` | "오픈 D-n" | "🔔 M/D 오픈 알림 받기" (알림톡 시뮬레이션) |
| 미리보기(`p:` 링크) | "미리보기" | 비활성 "상세페이지 미리보기 — 판매 링크 발급 전" |
| 그 외 **모든** 상태 — `CLEARING`·`SETTLED`뿐 아니라 아직 시작 전인 샘플·테스트·제안 단계(`SAMPLE_REQUESTED`~`TESTING`, `SCHEDULE_PROPOSED`)와 `REJECTED`·`PASSED` 등 포함 | "판매 종료" | 비활성 "판매가 종료되었습니다" · "교환·환불은 종료 후 21일까지 셀러리 고객센터에서 처리됩니다" |

- 링크 만료 = 링크 자체는 계속 열리되 **구매가 막히고 "판매 종료" 표시**로 바뀌는 것. 404가 되지는 않는다.
- **미정(코드 미구현) — 시작 전 링크 문구:** `#s/cN`은 상태를 보지 않으므로(6장) 일정이 잡히기 전 캠페인의 링크로 들어와도 "판매 종료"·"판매가 종료되었습니다"가 표시된다 — 열린 적 없는 판매에 종료 문구가 붙는 셈이다. `vStore`의 분기는 `LIVE` / `SCHEDULE_CONFIRMED` / 미리보기 / 그 외 네 가지뿐이라, 실서비스에서는 시작 전 상태에 "준비 중" 표시를 두거나 확정 전에는 링크를 열지 않도록 결정 필요.
- `CLEARING` 중 환불은 정산액에서 차감된다. `SETTLED` 이후 주문은 환불 처리할 수 없다("별도 CS 정산 조정 필요").
- 고객 안내(구매 페이지·FAQ): 판매 종료 후 21일 동안 교환·환불 신청 가능(단순 변심 7일 · 하자 21일).
- 관리자 시뮬레이션 버튼: "판매 시작 처리"(`goLive` — 시작일이 미래면 오늘로 당김), "판매 종료 처리"(`endCamp` — 종료일을 오늘로), "⏩ 3주 경과 처리"(`ffwd` — 종료일을 21일 전으로).

> **제안서 표기:** "종료되면 링크가 만료되고 가격이 돌아갑니다"(브랜드 p.8), FAQ "판매 기간이 끝나면 정가로 돌아갑니다" — 링크 만료(구매 차단)는 구현, **가격 복귀는 미정(코드 미구현)**: 종료된 페이지에도 판매가가 그대로 표시된다. "D+21 자동 정산·자동 입금"(양쪽 제안서) — 기준일 산출은 구현, **지급 자동 실행은 미정(코드 미구현)**: 관리자가 "정산 실행" 버튼으로 처리한다.

## 8. 링크 진입 보호 (LINKCTX)

인플루언서 링크로 들어온 방문은 브라우저에 기억해서, 홈으로 이동하거나 새로고침해도 경쟁 판매가 계속 보이지 않게 한다.

### 8.1 저장과 해제

| 항목 | 규칙 |
|---|---|
| 저장소 | `localStorage['slry-linkctx'] = {cid, at}` (`LINKCTX_KEY`). 메모리에는 `S.linkCtx = {cid}` |
| 설정 시점 | `#s/cN` 또는 `#link/cN` 해시로 진입할 때(첫 로드 · 해시 변경 모두). 새 링크로 들어오면 덮어쓴다 |
| 유지 | 새로고침 · "← 셀러리 홈"(`storeBack`) · "다른 판매 보기" · 카테고리 전환 · 인플루언서 선택 · 셀러리 소개의 "브랜드 센터·인플루언서 센터" 버튼(`goCenter`, 6장) — 모두 유지 |
| 해제 ① | 페이지 로드 시 해당 캠페인이 데이터에 없으면(캠페인 삭제·초기화) 해제 |
| 해제 ② | 페이지 로드 시 `종료일`이 있고 **오늘 − 종료일 > 7일**이면 해제 |
| 해제 ③ | 관리자 "시드 초기화"(`reset`) |
| 주의 ① | 해제 판정은 **페이지 로드 시점**(`loadLinkCtx`)에만 실행된다. 열어 둔 탭에서 판매가 끝나도 다음 로드 전까지는 보호가 유지된다 |
| 주의 ② | `#s/cN`은 상태와 무관하게 존재하는 캠페인이면 모두 받으므로(6장), **시작·종료일이 없는 캠페인**(샘플 요청·배송·테스트·제안 단계) 링크로 들어오면 해제 ②가 적용될 날이 오지 않는다 → 캠페인이 삭제되거나(①) 시드가 초기화될 때까지(③) 보호가 유지된다 |

### 8.2 무엇이 보이고, 무엇이 안 보이나 (`custVisible`)

링크 컨텍스트가 없는 방문(판매센터 직접 진입 · `S.linkCtx` 없음)에는 **필터가 없다** — `custVisible`은 `!S.linkCtx`이면 무조건 true를 돌려주므로, 같은 상품·같은 카테고리의 판매가 "진행 중"·카테고리 건수·실시간 판매 순위에 나란히 노출된다. 3.2의 기간 공유로 같은 주에 겹치도록 허용된 판매도 그 상태 그대로 판매센터에 함께 보인다(시드: 지유 c1 버닝온 LIVE와 유나 c12 치팅온 LIVE — 같은 브랜드 · 같은 다이어트·체형 카테고리 — 가 나란히). 브랜드 p.8 헤드라인 "같은 상품, 같은 카테고리는 같은 자리에 나오지 않습니다"와 p.3 "판매가 서로 겹쳐요"는 **링크 방문자에 대해서만** 성립한다(3.3 제안서 표기 참조).

보호 중인 링크의 캠페인을 L(인플루언서 · 상품 · 카테고리)이라 할 때, 고객 홈의 "진행 중" · "오픈 예정" · 카테고리 건수 · 실시간 판매 순위와 "인플루언서" 탭의 건수는 다음 규칙으로 걸러진다.

| 보임 | 항목 | 규칙 |
|---|---|---|
| ✓ | 지금 보고 있는 그 판매 | L 자신 |
| ✓ | 같은 인플루언서의 다른 진행 중·예정 판매 | `sellerId`가 L과 같으면 무조건 보임. 구매 페이지 하단 "○○님의 다른 판매"(`LIVE`·`SCHEDULE_CONFIRMED`)로도 노출 |
| ✓ | 다른 상품 **이면서** 다른 카테고리인 타 인플루언서 판매 | 상품 ≠ L.상품 **AND** 카테고리 ≠ L.카테고리 |
| ✓ | 셀러리 인증 띠 · 인증 확인 모달 · 브랜드 사업자 정보 · 배송/교환/환불 안내 | 필터 대상 아님 |
| ✓ | 홈 "인플루언서" 칩 목록(공개 프로필) · 셀러리 소개 | 필터 대상 아님. 인플루언서를 고르면 그 사람의 판매만 보이되 위 규칙은 계속 적용 |
| 필터 적용 | "인플루언서" 탭(`vCustInfluencers`)의 인플루언서별 건수 — 진행 중 · 오픈 예정 · 완료 | 각 인플루언서의 캠페인에 `custVisible`을 적용해 센다 — 보호 중이면 경쟁 판매는 건수에서도 빠진다 |
| ✕ | 같은 상품을 파는 다른 인플루언서의 판매 | 상품 = L.상품 |
| ✕ | 같은 카테고리의 경쟁 상품 | 카테고리 = L.카테고리. **브랜드 구분 없음** — `custVisible`은 `brandId`를 보지 않으므로 같은 브랜드의 다른 상품도 카테고리가 같고 인플루언서가 다르면 숨는다(시드: `#s/c1`(지유 · 버닝온) 방문자에게 같은 바인허브의 치팅온 c12(유나)가 비노출) |
| ✓ | 다른 브랜드의 추천·배너 — 셀러리 샵 "고객 홈 상단 노출(7일)"로 최상단에 고정된 타 브랜드 판매(★ 추천 배지) | `custVisible`은 상품·카테고리만 보므로 **카테고리가 다르면 그대로 보인다**. 상단 노출을 산 타 브랜드의 판매는 링크 방문자에게도 "진행 중"·"오픈 예정" **최상단**에 ★ 추천으로 노출된다(10장). 프로토타입에 별도 배너 영역은 없다 |

### 8.3 안내 문구

고객 홈 상단: "🔗 **○○**님의 판매 링크로 들어오셨어요 — 이 판매와 같은 상품·카테고리의 다른 판매는 표시되지 않습니다. (판매 종료까지 유지)"

> 문구는 "판매 종료까지"라고 하지만 코드는 **종료 후 7일**까지 유지한다(8.1 해제 ②). 실서비스 전 문구 또는 기간 중 하나로 통일 필요.

> **제안서 표기:** 브랜드 p.8 · 인플루언서 p.9의 ✓/✕ 목록 중 다섯 항목(그 판매 · 같은 인플루언서의 다른 판매 · 인증/브랜드 정보/환불 안내 · 같은 상품 ✕ · 같은 카테고리 ✕)은 8.2와 일치 — 단 "같은 카테고리의 경쟁 상품 ✕"는 브랜드를 가리지 않아 **자사의 다른 상품**도 숨는다(8.2 행 참조). "경쟁 상품"이라는 표현에서 브랜드가 기대하지 않을 부분이므로 브랜드 안내에 명시 필요. **"다른 브랜드의 추천·배너 ✕"는 코드와 다르다** — 프로토타입에 배너는 없지만 유료 추천 요소(고객 홈 상단 노출 · ★ 추천)가 있고, 카테고리가 다른 타 브랜드의 상단 노출 판매는 링크 방문자에게도 최상단에 보인다. 실서비스 전에 링크 방문자에게 타 브랜드 `homeFeatured` 카드를 숨길지(제안서대로) 또는 제안서 문구를 고칠지 결정 필요.

## 9. 캘린더 표시 규칙 (`calHtml`)

| 화면 | 대상 캠페인 | 라벨 |
|---|---|---|
| 인플루언서 "내 캠페인" 탭 하단 "판매 캘린더 — 내 스케줄 한눈에" (`vSellerCamps`) | 내 캠페인 | 상품명 |
| 브랜드 "내 캠페인" 하단 "판매 캘린더 — 브랜드 스케줄 한눈에" (`vBrandCamps` → `calHtml({brandView:true})`) | 내 상품의 캠페인 전체 | 상품명 · 인플루언서명 |

인플루언서 홈(`vSellerHome`)에는 캘린더가 없다 — 인플루언서 쪽 호출은 `vSellerCamps` 한 곳뿐이다.

| 이벤트 | 조건 | 범례 | 클릭 |
|---|---|---|---|
| 확정 (`plan`) | `SCHEDULE_CONFIRMED`, 시작~종료일 | 확정 | 캠페인 스레드 |
| LIVE (`live`) | `LIVE`, 시작~종료일 | LIVE | 캠페인 스레드 |
| 종료·정산중 (`done`) | `CLEARING`·`SETTLED`, 시작~종료일 | 종료·정산중 | 캠페인 스레드 |
| 정산일 (`pay`) | `CLEARING`이고 날짜 = 종료 + 21일 | "₩ 정산 예정" | 정산 탭 |
| 테스트 마감 (`due`) | `TESTING`이고 날짜 = `testDue` | 테스트 마감 | 캠페인 스레드 (표시 전용 · 2.1) |

- 기간 이벤트는 **첫날에만 이름**을 쓰고 이후 날짜는 같은 색 바로 이어진다. 월 이동 ‹ › 와 "오늘" 버튼.
- `SCHEDULE_PROPOSED`(승인 대기)는 `calHtml`의 상태 목록(`SCHEDULE_CONFIRMED` / `LIVE` / `CLEARING` / `SETTLED`)에 없어 표시되지 않는다 — `propStart`/`propEnd`는 캘린더에 반영되지 않는다(`start`가 남아 있어도 상태 때문에 제외).
- 다른 인플루언서가 잡은 기간은 인플루언서 캘린더에 표시되지 않는다. 인플루언서·브랜드 센터 안의 직접 확인 경로는 두 곳 — 일정 제안 모달의 "이 상품의 확정 기간" 목록("M/D – M/D @핸들 확정")과 브랜드 상품 관리 표의 "판매 일정" 열. 그 밖에 **간접 경로**가 있다: 고객 화면 홈(상단 "고객 화면" 탭으로 누구나 진입)의 "오픈 예정" 카드는 모든 `SCHEDULE_CONFIRMED` 캠페인을 시작일 · 인플루언서 이름 · **등급 배지**와 함께, "진행 중" 카드는 모든 `LIVE` 캠페인을 기간과 함께 보여주고(`vCustHome` · `custCard`), 상품 상세 모달의 실적 표(`productDetailModal`)는 `LIVE`·`CLEARING`·`SETTLED` 캠페인의 기간을 보여준다(확정 단계는 제외 · 첫 행 외에는 매출 데이터 확인권 필요). **모달 목록은 기간과 핸들만 표시하고 보유자 등급은 표시하지 않으므로**, 골드 이하 인플루언서는 인플루언서 센터 안에서는 어느 기간이 플래티넘 이상 선점인지 알 수 없고(고객 화면으로 우회해야 등급이 보인다) 진입 가능 여부는 "승인 요청 보내기"를 눌러 토스트를 받아야 알 수 있다.

> **제안서 표기:** 캘린더 예시의 "배정 불가"(브랜드 p.8) · "타 판매 확정"(인플루언서 p.9) 셀 — 미정(코드 미구현). 확정 기간 목록의 보유자 등급 표시도 미정(코드 미구현). 코드는 진입 가능 여부를 제안·승인 시 토스트로만 알린다.

> **미정(코드 버그) — 샵 카드 만료 표시 · 환급 처리:** ① `SHOP`의 인플루언서·브랜드 `homefeature` 항목 모두 `days` 필드가 없어(`isHomeFeat`의 7일 판정과는 별개) 셀러리 샵 카드는 한 번 사면 영구히 "보유 중"으로 표시되고 재구매 버튼이 나오지 않는다 → 7일이 지나도 다시 살 수 없어 **계정당 1회용**이 된다. ② 대상 캠페인이 없을 때 `buyItem`은 원장 항목만 `pop()`하고 그 **전에** 기록한 `celeryItems.homefeature`는 남겨 두므로, 셀러리는 돌아오지만 카드가 "보유 중"이 되어 판매가 생긴 뒤 다시 시도할 수 없다. 코드 수정 과제: `homefeature`에 `days:7` 추가(`regongu`는 `days:30` · 2.4) · `celeryItems` 기록을 대상 검사 뒤로 이동.
